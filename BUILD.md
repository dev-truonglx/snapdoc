# Build & Release Guide

This covers everything beyond `npm run app:dev`: producing a signed local
build, setting up updater/code-signing keys, and cutting a release. For
day-to-day development (no signing keys needed), see
[CONTRIBUTING.md](CONTRIBUTING.md).

## Requirements

- Node.js ≥ 20, Rust ≥ 1.80 (tested with Node 22 / Rust 1.96)
- macOS builds: Xcode command line tools
- Windows installer builds: either a Windows machine, or Docker Desktop for
  cross-building from macOS/Linux (see [Windows builds](#windows-builds))
- `ffmpeg` sidecar binary — fetched automatically before every dev/build run
  by `scripts/fetch-ffmpeg.mjs` (wired into `beforeDevCommand` /
  `beforeBuildCommand` in `tauri.conf.json`). Nothing to do manually; it
  downloads a static build per target triple into `src-tauri/binaries/`
  (gitignored) if not already present.

## Plain (unsigned) build

```bash
npm install
npm run app:build     # tauri build → .dmg (macOS) / .msi,.exe (Windows)
```

This works out of the box with no keys — it just won't produce
auto-update artifacts, and on macOS the Screen Recording permission will be
re-requested on every rebuild (see below).

## macOS dev signing

`tauri dev` produces an ad-hoc-signed binary whose code identity changes on
every build. macOS ties the Screen Recording (TCC) permission to that
identity, so it gets revoked on every rebuild and captures come back black.

`scripts/dev-mac.sh` (via `npm run dev:mac`) works around this by signing
debug builds with a **stable, throwaway, self-signed identity** that
persists across rebuilds:

```bash
npm run dev:mac
```

- First run: grant **Screen Recording** to SnapDoc in System Settings →
  Privacy & Security, quit the app, run `npm run dev:mac` again.
- Subsequent runs keep the same identity, so the grant survives.
- The identity's private key is stored at `~/.tauri/snapdoc-codesign.p12`
  (self-signed, no Apple trust — it only exists to keep a stable code
  identity locally). It's generated automatically by
  `scripts/macos-codesign.sh` the first time you run `dev:mac` or
  `build:mac`; there's nothing to download or request access to.
- To re-sign an arbitrary bundle by hand: `npm run sign:mac [path/SnapDoc.app]`.

This identity is **not** used for release builds — it has no bearing on
distributing the app to other users. It exists solely so *your own machine*
doesn't keep nagging you for permission during development.

## Signing keys

There are two **separate** keys involved in producing a real release, both
distinct from the throwaway dev identity above:

| Key | Purpose | Where it lives |
|---|---|---|
| **Updater key** (minisign keypair) | Signs release artifacts so `tauri-plugin-updater` can verify auto-update packages before installing them | Private half: `~/.tauri/snapdoc-updater.key` (never committed). Public half: embedded in `src-tauri/tauri.conf.json` |
| **macOS code-signing identity** (Developer ID `.p12`) | Signs/notarizes the `.app`/`.dmg` for distribution outside the Mac App Store | Private half: `~/.tauri/snapdoc-codesign.p12` (never committed, encrypted backup only) |

**Only maintainers who cut releases need these.** Contributors sending PRs
don't need either key — `npm run app:dev` / `npm run dev:mac` work without
them (dev builds just skip updater artifact signing).

### One-time setup (maintainers only)

```bash
npm run setup:keys        # generates the updater keypair, writes the
                           # public key into src-tauri/tauri.conf.json
```

Follow the script's output: commit the resulting `tauri.conf.json` change
(the *public* key is safe to commit), then back up the private key:

```bash
npm run backup:keys        # encrypts both keys with a passphrase you choose,
                            # writes secrets/*.enc — SAFE to commit
```

`secrets/*.enc` files are AES-256/PBKDF2-encrypted and fine to have in the
repo, but the passphrase itself is **not** stored anywhere in git — keep it
in a password manager. Anyone who can decrypt the updater key can push a
malicious auto-update to every SnapDoc install, so treat that passphrase
with the same care as a production deploy credential.

To restore keys onto a new machine:

```bash
npm run restore:keys       # prompts for the passphrase, writes keys back to ~/.tauri/
```

### macOS Developer ID identity

The `.p12` used for real distribution (notarization-eligible) is separate
from the `snapdoc-codesign.p12` dev identity described above, and is not
generated by any script here — it comes from your Apple Developer account.
Import it into your keychain and set `APPLE_SIGNING_IDENTITY` /
`APPLE_ID` / notarization credentials as environment variables before
running a release build (see `scripts/build-mac.sh` and
`scripts/release-all.sh` for the exact variables each step reads).

## Signed local build

```bash
npm run build:mac         # = scripts/build-mac.sh — signed .app/.dmg,
                           # updater artifacts if the key is present
```

## Windows builds

Two options:

- **On a Windows machine**: `npm run app:build` produces `.msi`/`.exe`
  directly.
- **Cross-build from macOS/Linux via Docker** (no Windows machine needed):

  ```bash
  scripts/build-win-docker.sh
  ```

  Builds the NSIS installer inside a Linux container (`scripts/win-cross.Dockerfile`)
  and writes `dist-win/SnapDoc_<ver>_x64-setup.exe` (+ `.sig` if the updater
  key is present). Requires Docker Desktop running.

## Cutting a full release (maintainers only)

```bash
scripts/release-all.sh v1.2.4 "Fix scroll capture memory limit, add region remember option"
```

One-shot: builds a macOS universal binary natively + the Windows installer
via Docker, and publishes both as a **draft** GitHub release (with a unified
`latest.json` for the updater) to the repo configured as `RELEASES_REPO` in
that script. Review the draft, then publish it manually to ship the update
to all users.

The description argument becomes the "What's new" section of the release
notes:

- Omit it and the script prompts for a one-line description interactively.
- Pass a longer changelog from a file instead: `--notes-file CHANGELOG.md`.
- Re-running the script for a tag that already has a draft release just
  updates its notes (and re-uploads the build artifacts) rather than
  failing.

Prerequisites: `gh auth login` with push access to the releases repo,
Docker Desktop running, `rustup` installed, and the updater key restored
locally (`npm run restore:keys` if it's a fresh machine).

## CI

A build workflow for macOS + Windows lives at
`.github/workflows/build.yml_bk` (currently disabled — rename it to
`build.yml` to enable it as a PR check). It only compiles the app to catch
build breakage; it never touches the signing/updater keys and never
publishes a release. Releases are cut locally by maintainers via
`scripts/release-all.sh`.
